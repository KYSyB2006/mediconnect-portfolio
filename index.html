Cas 1 — Périmètre P2

Recherche & géolocalisation

Comment un patient trouve-t-il un médecin disponible près de chez lui, et comment le mesurer ?

Cas d'étude — méthode CAR

Trier les médecins par pertinence géographique, pas juste par nom

CContexte

Sans distance calculée, un patient doit ouvrir chaque fiche pour savoir si un médecin est proche. Il fallait une recherche filtrable par spécialité et par rayon, avec la distance réelle affichée — et un moyen de vérifier que cette recherche répond vraiment au besoin.

src/controllers/api/AnalyticsApiController.php 
SELECT
    COALESCE(NULLIF(TRIM(u.ville), ''), 'Inconnu') AS ville,
    COUNT(m.id)                                     AS nb_medecins,
    COUNT(DISTINCT m.specialisation)                AS nb_specialites
FROM medecins m
JOIN utilisateurs u ON u.id = m.utilisateur_id
WHERE u.statut = 'actif' AND m.latitude IS NOT NULL
GROUP BY ville
ORDER BY nb_medecins DESC;

L'écart saute aux yeux : les deux spécialités les plus recherchées — dentiste et neurologue, 24 recherches chacune — comptent respectivement 0 et 2 praticiens, et le kinésithérapeute (5e demande) est lui aussi totalement absent du référentiel. À l'inverse, la médecine générale concentre 17 des 49 praticiens, soit 35 % de l'offre, pour seulement 14 recherches.

Recommandation : ouvrir le référentiel aux spécialités absentes (dentiste, kinésithérapeute, rhumatologue) avant d'élargir le recrutement de généralistes. Le visuel « spécialités non trouvées par rayon » du rapport confirme ce diagnostic du côté des échecs de recherche.
Cas 2 — Périmètre P3

Rendez-vous & disponibilités

Une fois le bon médecin trouvé, encore faut-il savoir quels créneaux sont réellement libres.

Cas d'étude — méthode CAR

Un créneau "disponible" doit tenir compte de l'agenda réel du médecin

CContexte

Les horaires hebdomadaires d'un médecin ne suffisent pas : il faut en soustraire les rendez-vous déjà pris pour ne proposer au patient que des créneaux réellement libres, sans risque de double réservation.

AAction
src/models/RdvModel.php — creneauxDisponibles() 
// Génère les créneaux d'une journée : horaires - RDV déjà pris
foreach ($horaires as $h) {
    $debut = strtotime($date . ' ' . $h['heure_debut']);
    $fin   = strtotime($date . ' ' . $h['heure_fin']);

    while ($debut + $dureeMin * 60 <= $fin) {
        $heure = date('H:i', $debut);
        $creneaux[] = [
            'heureDebut' => $heure,
            'heureFin'   => date('H:i', $debut + $dureeMin * 60),
            'disponible' => !isset($pris[$heure]),  // $pris = RDV déjà réservés ce jour
        ];
        $debut += $dureeMin * 60;
    }
}
Pourquoi c'est une question de données, pas juste de code : la disponibilité découle de trois sources croisées (horaires_semaine, rendez_vous, durée de consultation propre à chaque médecin) — traduire cette règle métier en requêtes fiables limite les doubles réservations, le problème numéro un d'un système de RDV.
scripts/export_powerbi.php 
SELECT
    u.nom AS medecin_nom, r.statut, COUNT(*) AS nb_rdv,
    ROUND(AVG(TIMESTAMPDIFF(HOUR, r.created_at, r.date_heure)), 1) AS delai_moyen_heures
FROM rendez_vous r
JOIN medecins m ON m.id = r.medecin_id
JOIN utilisateurs u ON u.id = m.utilisateur_id
GROUP BY mois, medecin_nom, r.statut
ORDER BY mois ASC, nb_rdv DESC; -- alimente le dashboard Power BI Activité
RRésultat

L'algorithme alimente le parcours de prise de RDV de l'application — le patient ne voit que les créneaux encore libres — et la requête ci-dessus alimente le dashboard Power BI Activité avec le délai moyen entre demande et rendez-vous, par médecin et par mois.

Limites assumées : le calcul filtre les créneaux à l'affichage ; seule une contrainte d'unicité en base garantit que deux patients ne réservent pas le même créneau à la même seconde. Par ailleurs, le schéma prévoyait une collection MongoDB activity_logs (création/annulation de RDV) pour enrichir l'analyse comportementale — elle est initialisée avec ses index mais n'a pas été branchée à l'API dans le temps du projet. Le suivi d'activité repose donc aujourd'hui sur MySQL uniquement (délai moyen, volumes par statut), pas encore sur l'historique d'événements Mongo.
